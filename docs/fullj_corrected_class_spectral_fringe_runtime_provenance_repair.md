## Diagnosis

That comparison used the wrong provenance object. `CORRECTED_SOURCE_SHA` is the hash of the earlier corrected AeST source before the complete local dense-k64 runtime patch chain. The dense-k64 setup deliberately applies later validated patches after the baseline AeST source, including the finite-memory accessors and the variational-forcing helper. In particular, `v019j/apply_memory_patch.py` and `v019w/apply_variational_forcing_patch.py` modify `source/aest_memory.c` itself. Therefore the final dense-k64 runtime source cannot equal the earlier baseline-source SHA by construction.

The local dense-k64 environment is generated by `fullj_weyl/setup_corrected_class_dense_k64_local.sh`, which deterministically resets CLASS to the frozen official head and applies the already locked patch sequence before installing `classy`. The k-file-capacity patch changes only `include/perturbations.h`, not `source/aest_memory.c`.

This is a provenance-bookkeeping defect, not a physics or numerical result.
